# find-internet-speed

Консольный скрипт на Python: качает один и тот же адрес 10 раз подряд, дожидаясь
полного ответа на каждый запрос, и печатает среднее время запроса, суммарный
объём скачанного и скорость скачивания.

Без сторонних зависимостей — только стандартная библиотека (включая тесты).
Для инструмента, который открывает TLS-соединения, это сознательный выбор:
нечего ставить, нечего обновлять, нет supply-chain-рисков.

## Требования

* Python 3.10+
* ОС: macOS / Linux / Windows

## Быстрый старт

```bash
git clone git@github.com:st3ir/find-internet-speed.git
cd find-internet-speed
```

Запуск прямо из папки, без установки:

```bash
python3 -m speedmeter "https://speed.cloudflare.com/__down?bytes=1000000"
```

Либо установить как пакет и получить команду `speedmeter`:

```bash
pip install -e .
```

```bash
speedmeter "https://example.com/heavy-image.jpg"
```

## Единицы измерения

| Величина | Единицы | Пояснение |
|---|---|---|
| Скорость скачивания | **Mbit/s** (10⁶ бит/с), в скобках **MiB/s** (2²⁰ байт/с) | Mbit/s — то, в чём скорость указывают провайдеры, поэтому он основной; MiB/s удобнее сопоставлять с размером файла |
| Объём скачанного | **KiB / MiB / GiB** (1 KiB = 1024 B) + точное число байт | Двоичные приставки по IEC, чтобы не путать с 10⁶ |
| Время запроса | **мс** до одной секунды, дальше **с** | |

В JSON-выводе единица измерения входит в имя ключа: `total_bytes`,
`average_seconds`, `speed_mbit_per_second`, `speed_mib_per_second`.

### Как считается скорость

```
скорость = суммарный объём / суммарное время всех запросов
```

* **Суммарное время** — сумма длительностей 10 запросов. В длительность одного
  запроса входит всё: DNS, TCP-handshake, TLS-handshake, время до первого байта
  и чтение тела до конца. То есть это честная *клиентская* скорость скачивания
  ресурса, а не чистая пропускная способность канала.
* Каждый запрос идёт с заголовком `Connection: close`, поэтому все 10 замеров
  одинаковы по составу — каждый включает свой handshake.
* `Accept-Encoding: identity` — сервер не сжимает ответ, и измеренные байты
  равны реально прошедшим по сети (а не распакованным).
* `Cache-Control: no-cache` просит промежуточные кеши не отвечать своей копией.
  URL при этом не меняется (никаких cache-busting-параметров), чтобы не ломать
  подписанные ссылки.
* В отчёте есть `Fastest / slowest`: по разбросу видно, насколько прогрев
  соединения и CDN повлияли на средний результат.

## Параметры

```
speedmeter [-h] [-n N] [-t SECONDS] [--chunk-size BYTES] [--max-bytes BYTES]
           [--ca-bundle PATH] [--allow-plaintext-http] [--json] [-q] [--version]
           url
```

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `url` | — | Адрес, к которому стучаться (например, тяжёлая картинка) |
| `-n`, `--requests` | `10` | Сколько последовательных запросов сделать |
| `-t`, `--timeout` | `30` с | Таймаут одного запроса |
| `--chunk-size` | `65536` | Размер блока чтения из сокета |
| `--max-bytes` | `1 GiB` | Отказаться от ответа больше этого размера |
| `--ca-bundle` | автоопределение | PEM-файл с доверенными корневыми сертификатами |
| `--allow-plaintext-http` | выключено | Разрешить `http://` (без шифрования) |
| `--json` | выключено | Отчёт в JSON вместо текста |
| `-q`, `--quiet` | выключено | Не печатать прогресс по запросам |

Коды возврата: `0` — успех, `1` — ошибка соединения или политики безопасности,
`2` — неверные аргументы, `130` — прервано по Ctrl+C.

## Безопасность соединения

Всё, что относится к безопасности, собрано в одном модуле
[`speedmeter/security.py`](speedmeter/security.py) — одно место для аудита.

**Куда разрешено подключаться** (`UrlPolicy`)

* только `https://`; `http://` — лишь при явном `--allow-plaintext-http`,
  остальные схемы (`file://`, `ftp://`, …) запрещены всегда;
* политика применяется заново **к каждому редиректу**, поэтому сервер не может
  ответить `302` и увести замер с HTTPS на открытый HTTP;
* логин/пароль в URL запрещены — они утекают в логи, прокси и `Referer`;
* переменные окружения `*_proxy` игнорируются: неожиданный прокси — это и
  man-in-the-middle, и искажённый замер.

**Как устроен TLS** (`create_tls_context`)

* обязательная проверка цепочки сертификатов и совпадения имени хоста
  (`CERT_REQUIRED` + `check_hostname`);
* минимум TLS 1.2 — TLS 1.0/1.1 и SSLv3 отключены;
* только шифры с forward secrecy и AEAD: `ECDHE+AESGCM:ECDHE+CHACHA20`
  (без CBC, без RSA key transport);
* `VERIFY_X509_STRICT` — строгая проверка соответствия сертификата RFC 5280;
* отключены TLS-компрессия (CRIME) и renegotiation;
* ALPN объявляет ровно тот протокол, который мы умеем (`http/1.1`).

**Чего в скрипте намеренно нет** — флага вроде `--insecure` / `verify=False`.
Замер скорости не стоит того, чтобы доверять непроверенному собеседнику.
Если доверенных корневых сертификатов не нашлось, скрипт не продолжает работу
без проверки, а падает с понятной ошибкой.

**Защита от «плохого» ответа**

* `--max-bytes`: ответ, который больше лимита, отклоняется — и по заголовку
  `Content-Length`, и в процессе чтения потока;
* `Accept-Encoding: identity` снимает риск decompression bomb;
* таймаут на каждый запрос, тело читается потоком по 64 KiB и никогда не
  складывается целиком в память.

### Если сертификаты не находятся

Сборки python.org на macOS идут со своим OpenSSL, который не читает Keychain,
поэтому хранилище корневых сертификатов может оказаться пустым:

```
error: no CA certificates available to verify the server with; install certifi (pip install certifi) or pass --ca-bundle PATH
```

Скрипт сам подхватывает `certifi`, если он установлен, иначе — системный бандл
(`/etc/ssl/cert.pem` на macOS, `/etc/ssl/certs/ca-certificates.crt` на Debian и
т. д.). Если ни того, ни другого нет, путь можно указать явно:

```bash
python3 -m speedmeter --ca-bundle /etc/ssl/cert.pem "https://example.com/image.jpg"
```

## Тесты

83 теста на стандартном `unittest`, ставить ничего не нужно:

```bash
python3 -m unittest discover -v
```

Если привычнее pytest — он тоже подхватывает эти тесты (`pytest`).

Что покрыто:

* `test_security.py` — политика URL (схемы, редиректы, креды в URL) и настройки
  TLS-контекста (версия, шифры, флаги проверки);
* `test_transport.py` — HTTP-слой на подставном opener, без сети: заголовки,
  таймаут, лимит размера, перевод ошибок `urllib` в свои;
* `test_measurement.py` — цикл замера на фейковых транспорте и часах: ровно 10
  запросов, подсчёт байт, среднее время, прогресс-колбэк;
* `test_models.py`, `test_formatting.py`, `test_reporting.py` — арифметика,
  единицы измерения, текстовый и JSON-вывод;
* `test_cli.py` — разбор аргументов, коды возврата, разделение stdout/stderr;
* `test_integration.py` — сквозные прогоны через реальный сокет на локальном
  сервере: 3 последовательных скачивания, редирект, 404, превышение лимита,
  отказ от `http://` без флага и **отказ от самоподписанного сертификата**
  (проверка, что строгий TLS действительно работает).

## Структура

```
speedmeter/
├── security.py      политика URL + строгий TLS-контекст
├── transport.py     HTTP: URL -> поток байт (urllib), безопасные редиректы
├── measurement.py   цикл замера: N запросов, таймеры, прогресс
├── models.py        RequestSample / MeasurementReport и вся арифметика
├── formatting.py    масштабирование величин и единицы измерения
├── reporting.py     рендереры отчёта: текст и JSON
├── config.py        неизменяемая конфигурация запуска + валидация
├── errors.py        иерархия исключений
├── app.py           composition root: сборка объектов воедино
└── cli.py           argparse, вывод, коды возврата
```

Принципы, по которым разложено именно так:

* **SRP** — у каждого модуля одна причина для изменения. Поменять единицы
  измерения — `formatting.py`, добавить формат вывода — `reporting.py`,
  ужесточить TLS — `security.py`. Сетевой код не знает про печать, цикл замера
  не знает про сокеты.
* **DIP** — `SpeedMeter` зависит от протокола `Transport`, а не от `urllib`;
  часы и слушатель прогресса тоже внедряются. Поэтому цикл замера тестируется
  без сети и без `sleep`, а конкретные классы связываются в одном месте —
  `app.py`.
* **OCP** — новый формат вывода добавляется новым классом с методом `render`,
  существующий код не меняется.
* **DRY** — одна функция масштабирования единиц на все величины; одна
  `UrlPolicy`, которую переиспользуют и проверка аргумента, и каждый редирект.
* **KISS** — только стандартная библиотека, без фреймворков, без асинхронности
  там, где по условию запросы последовательны.

## Ответы на вопросы

### Как использовался ИИ при решении

Код написан в паре с Claude (Claude Code): я ставил задачи и ограничения
(«только stdlib», «безопасность на максимум», «SOLID/DRY/KISS», структура
модулей, какие тесты нужны), ИИ писал код и тесты, я проверял результат
и правил направление.

Где это реально ускорило работу:

* черновик обвязки — argparse, dataclass-модели, рендереры, тесты-двойники
  (fake transport, fake clock, fake opener) — то, что пишется по шаблону;
* чек-лист по TLS: что ещё можно прикрутить к `ssl.SSLContext`
  (`VERIFY_X509_STRICT`, ограничение шифров, ALPN, запрет renegotiation) —
  быстрее, чем перечитывать документацию целиком;
* формулировки README.

Где пришлось вмешиваться руками — и это главное:

* **пустое хранилище сертификатов.** Первый же реальный запрос упал с
  `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`. Причина
  не в коде: сборка python.org на macOS не видит Keychain, а в venv не было
  `certifi`. Отключать проверку в инструменте «про безопасность» нельзя,
  поэтому появилось нормальное решение: автоопределение бандла
  (`certifi` → системный файл), явный `--ca-bundle` и громкая ошибка, если
  доверенных корней нет вообще;
* **проверка, а не доверие.** Все утверждения про безопасность закреплены
  тестами — в частности, сквозным тестом с самоподписанным сертификатом
  (клиент обязан отказаться) и тестом на блокировку редиректа с HTTPS на HTTP.
  Два теста на первом прогоне падали из-за ошибок в самих тестах — это ровно
  то, за чем нужен человек;
* решения по архитектуре (границы модулей, `Transport` как протокол, где
  валидировать URL) и по измерению (считать скорость как суммарный объём на
  суммарное время, не трогать URL ради cache-busting) принимались мной.

### Что улучшил бы, будь больше времени

1. **Статистика вместо среднего.** Среднее по 10 запросам чувствительно к
   выбросам. Добавил бы медиану и p95, стандартное отклонение, а также отдельно
   показывал бы время до первого байта (TTFB) и время передачи тела — сейчас
   они слиты в одну длительность, хотя смысл у них разный.
2. **Разогревочный запрос.** Первый запрос почти всегда медленнее (DNS, холодный
   TLS, холодный CDN). Сделал бы `--warmup N`, который не попадает в статистику.
3. **Параллельный режим.** По условию запросы последовательные, но канал
   одним потоком часто не насыщается. Добавил бы `--concurrency` и честно
   считал бы пропускную способность по wall-clock времени окна.
4. **CI и статический анализ.** GitHub Actions: матрица Python 3.10–3.13,
   `ruff`, `mypy --strict` (конфиги в `pyproject.toml` уже лежат), покрытие.
5. **Больше по безопасности:** проверка отзыва сертификатов (OCSP/CRL — в
   `ssl` из коробки неполноценно, нужен сторонний код), опциональный пиннинг
   публичного ключа (`--pin-sha256`), запрет резолва в приватные и loopback-адреса
   (защита от SSRF, если URL приходит извне), и ограничение числа редиректов
   своим значением вместо дефолтного.
6. **Детали UX.** Вывод в формате Prometheus textfile для регулярных замеров,
   `--output csv` для накопления истории, повтор при `429`/`5xx` с
   экспоненциальной задержкой (сейчас любая ошибка останавливает прогон —
   для замера это честно, но для мониторинга неудобно).
